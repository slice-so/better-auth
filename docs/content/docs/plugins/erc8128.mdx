---
title: ERC-8128
description: Authenticate requests with Ethereum wallets using HTTP Message Signatures
---

The ERC-8128 plugin adds [ERC-8128](https://erc8128.org) authentication to Better Auth — cryptographic request signing with Ethereum wallets, built on [HTTP Message Signatures (RFC 9421)](https://www.rfc-editor.org/rfc/rfc9421). Each signature binds to the HTTP method, path, headers, and body, giving you request integrity, replay protection, and an optional fully stateless flow.

The plugin supports two modes: **session-based sign-in** (sign once via `/erc8128/verify`, get a cookie, use sessions normally) and **per-request authentication** where every call is individually signed — ideal for autonomous agents and machine-to-machine calls.

## Usage

### Sign in (session creation)

Use `@slicekit/erc8128` to sign a request to `/erc8128/verify`. On success, Better Auth creates a user (if new), starts a session, and sets the session cookie.

```ts title="sign-in.ts"
import { createSignerClient, type EthHttpSigner } from "@slicekit/erc8128";
import { privateKeyToAccount } from "viem/accounts";

const account = privateKeyToAccount("0x...");

const signer: EthHttpSigner = {
  chainId: 1,
  address: account.address,
  signMessage: async (message) =>
    account.signMessage({ message: { raw: message } }),
};

const client = createSignerClient(signer);

const response = await client.fetch(
  "https://api.example.com/api/auth/erc8128/verify",
  { method: "POST" },
);
// Session cookie is set automatically in browsers.
```

### Per-request authentication (middleware)

When a request carries `Signature` + `Signature-Input` headers (or an `Authorization: ERC-8128 ...` header), the plugin's middleware verifies the signature automatically. Valid requests continue to your endpoint with the wallet identity resolved.

```ts title="signed-request.ts"
const response = await client.fetch(
  "https://api.example.com/api/protected",
);
```

<Callout>
  Middleware only intercepts requests routed through `auth.handler` (i.e. your Better Auth endpoints). For custom routes, call `verifyRequest()` from `@slicekit/erc8128` directly.
</Callout>

### Stateless mode

Set `createSession: false` for pure signature authentication without sessions. `/erc8128/verify` still verifies and creates/links users, but returns JSON only — no cookie.

```ts title="auth.ts"
erc8128({
  verifyMessage,
  createSession: false,
});
```

### Replayable signatures

Enable replayable signatures for short-lived automation or backend-to-backend calls where re-signing each request is impractical.

```ts title="auth.ts"
erc8128({
  verifyMessage,
  allowReplayable: true,
});
```

Invalidate previously issued replayable signatures with a signed `POST /erc8128/invalidate`:

```ts title="invalidate.ts"
await client.fetch("https://api.example.com/api/auth/erc8128/invalidate", {
  method: "POST",
  body: JSON.stringify({
    notBefore: Math.floor(Date.now() / 1000), // optional unix timestamp
  }),
});
```

### Browser wallets (viem)

Build an `EthHttpSigner` from any viem-compatible wallet — MetaMask, WalletConnect, or any injected provider:

```ts title="browser-signer.ts"
import { createSignerClient, type EthHttpSigner } from "@slicekit/erc8128";
import { createWalletClient, custom } from "viem";
import { mainnet } from "viem/chains";

const walletClient = createWalletClient({
  chain: mainnet,
  transport: custom(window.ethereum!),
});

const [address] = await walletClient.getAddresses();

const signer: EthHttpSigner = {
  address,
  chainId: mainnet.id,
  signMessage: async (message) =>
    walletClient.signMessage({ account: address, message: { raw: message } }),
};

const client = createSignerClient(signer);

// Sign in
await client.fetch("/api/auth/erc8128/verify", { method: "POST" });
```

## Route Policy

Use `routePolicy` to control per-route verification behavior in middleware.

```ts title="auth.ts"
erc8128({
  verifyMessage,
  routePolicy: {
    "GET /api/products/*": { replayable: true },
    "POST /api/orders": { replayable: false },
    "GET /api/public/*": false, // skip verification entirely
    default: { replayable: false }, // require auth on all other routes
  },
});
```

Matching order:

1. Exact match on `"METHOD /path"`.
2. Wildcard match (`*`).
3. `default` policy (if set).
4. No match + no default → opportunistic (passthrough on failure).

A value of `false` skips verification. A `VerifyPolicy` object requires verification — returning `401` on failure.

## Error Handling

When verification is required and fails, the response includes:

```json
{
  "error": "erc8128_verification_failed",
  "reason": "expired",
  "detail": "Signature has expired"
}
```

Along with `Accept-Signature` and `WWW-Authenticate` headers indicating the expected signature components.

## Caching & Storage

The plugin uses three different storage mechanisms, each with different durability requirements:

| Concern | Storage | Why |
| --- | --- | --- |
| **Nonce / replay protection** | Database (`verification` table) | Security-critical. A lost nonce could allow a replay attack. |
| **Signature invalidation** | Database (`erc8128Invalidation` table) | Security-critical. Losing state would re-enable revoked signatures. |
| **Verification cache** | `secondaryStorage` if configured, otherwise database, with in-memory L1 | Performance optimization only. A cache miss triggers a full re-verification — no security impact. |

### Verification cache

When `allowReplayable` is enabled, the plugin caches the result of successful replayable signature verifications so that subsequent requests carrying the same signature can skip the expensive cryptographic re-verification (which may involve on-chain RPC calls for ERC-1271 smart contract wallets).

If Better Auth's `secondaryStorage` is configured (e.g. Redis), the cache uses it automatically — entries are stored with a TTL matching the signature's remaining validity, shared across all instances. Otherwise, the cache falls back to the database (`verification` table) with a per-process in-memory read-through Map.

<Callout>
ERC-8128 involves cryptographic signature verification on every request. For production deployments, configure Better Auth's `secondaryStorage` (e.g. Redis) so the verification cache is shared across all server instances and survives restarts.
</Callout>

## Options

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `verifyMessage` | `VerifyMessageFn` | *required* | Signature verification function (use viem's `verifyMessage`). |
| `defaultPolicy` | `VerifyPolicy` | — | Default verification policy for middleware. |
| `createSession` | `boolean` | `true` | Create a Better Auth session on `/erc8128/verify`. |
| `sessionExpiresIn` | `number` | — | Session TTL in seconds. |
| `allowReplayable` | `boolean` | `false` | Enable replayable signatures and `/erc8128/invalidate`. |
| `maxValiditySec` | `number` | `300` | Maximum signature validity window (seconds). |
| `clockSkewSec` | `number` | `30` | Allowed clock skew (seconds). |
| `cacheSize` | `number` | `10000` | Max entries in the in-memory verification cache. Ignored when `secondaryStorage` is active. |
| `routePolicy` | `Record<string, VerifyPolicy \| false>` | — | Per-route middleware policy map. Keys are `"METHOD /path"` patterns. |
| `emailDomainName` | `string` | From `baseURL` | Domain for auto-generated user emails. |
| `anonymous` | `boolean` | `true` | If `false`, email is required on verify. |
| `ensLookup` | `Function` | — | ENS resolver for new user name/avatar. |

## Endpoints

| Method | Path | Description |
| --- | --- | --- |
| `POST` | `/erc8128/verify` | Verify a signed request, create/link user, start session. |
| `POST` | `/erc8128/invalidate` | Invalidate replayable signatures (requires `allowReplayable`). |
| `GET` | `/.well-known/erc8128` | Discovery metadata (algorithms, policies, endpoints). |

## Schema

### `walletAddress`

| Field | Type | Description |
| --- | --- | --- |
| `userId` | `string` | Reference to `user.id`. |
| `address` | `string` | Ethereum address. |
| `chainId` | `number` | EVM chain ID. |
| `isPrimary` | `boolean` | Primary wallet flag. |
| `createdAt` | `date` | Creation timestamp. |

### `erc8128Invalidation`

Stores both per-keyId invalidation timestamps and per-signature invalidation records.

| Field | Type | Description |
| --- | --- | --- |
| `keyId` | `string` | ERC-8128 key ID (`erc8128:<chainId>:<address>`). |
| `signature` | `string` | Signature hex for per-signature invalidation. Empty for per-keyId `notBefore` rows. |
| `notBefore` | `number` | Unix timestamp — signatures created before this are rejected. `0` for per-signature rows. |
| `expiresAt` | `number` | Unix timestamp when this invalidation record can be cleaned up. `0` for per-keyId rows. |
| `updatedAt` | `date` | Last update timestamp. |
