---
title: ERC-8128
description: Authenticate requests with Ethereum accounts using HTTP Message Signatures
---

[ERC-8128](https://erc8128.org) is a signature-based authentication standard built on [RFC 9421 (HTTP Message Signatures)](https://www.rfc-editor.org/rfc/rfc9421). The client signs each request with an Ethereum account and the server verifies it cryptographically, binding identity and intent to every request. Signatures can be request-bound or class-bound, with or without replay protection — controlled by the client, while the server always accepts the strongest posture (non-replayable, request-bound). Since no credential exchange or login is needed, authentication is zero-round-trip by design and the same flow works for browser users, backend services, and AI agents.

This plugin integrates ERC-8128 into Better Auth with two modes: **session-based authentication** (sign once via `/erc8128/verify`, get a session, use cookies normally) and **per-request authentication** where every call is individually signed. Better Auth handles the required server-side state — nonce tracking, signature invalidation, and verification caching — adding cryptographic request signing to your application with minimal operational complexity.

    <Step>

        ```ts title="auth-client.ts"
        import { createAuthClient } from "better-auth/client";
        import { erc8128Client } from "better-auth/client/plugins"; // [!code highlight]
        import { createWalletClient, custom } from "viem";
        import { mainnet } from "viem/chains";

        const wallet = createWalletClient({
            chain: mainnet,
            transport: custom(window.ethereum!),
        });
        const [address] = await wallet.getAddresses();

        export const authClient = createAuthClient({
            plugins: [
                erc8128Client({ // [!code highlight]
                    signer: { // [!code highlight]
                        address, // [!code highlight]
                        chainId: mainnet.id, // [!code highlight]
                        signMessage: (message) => // [!code highlight]
                            wallet.signMessage({ account: address, message: { raw: message } }), // [!code highlight]
                    }, // [!code highlight]
                }), // [!code highlight]
            ],
        })
        ```

## Usage

Clients authenticate by signing HTTP requests with the [`@slicekit/erc8128`](https://github.com/slice-so/erc8128) library.

### Authentication Modes

The plugin supports two distinct modes, used automatically based on the request headers. Both modes create users and wallet records automatically on first contact.

#### Session-based

**Session-based** authentication trades a single signed request for a session cookie — ideal for browser apps.

A signed `POST` to `/erc8128/verify` verifies the signature, creates a user (if new), starts a session, and sets the session cookie.

#### Per-request

**Per-request** authentication verifies a signature on every call with no sessions involved — suited for backend services, AI agents, and stateless APIs.

When any request to `auth.handler` carries ERC-8128 signature headers (`Signature` + `Signature-Input` or `Authorization: ERC-8128 ...`) and no valid session cookie is present, the middleware verifies it automatically before the endpoint runs. If the wallet is new, the middleware creates the user and wallet record — no prior call to `/erc8128/verify` is needed. The middleware does not create sessions — each request is authenticated individually by its signature.

<Callout>
  The middleware only runs for requests routed through `auth.handler`. For custom routes outside Better Auth, use `verifyRequest()` from `@slicekit/erc8128` directly.
</Callout>

## Route Policy

Use `routePolicy` to control per-route verification behavior in middleware.

```ts title="auth.ts"
erc8128({
  verifyMessage: publicClient.verifyMessage,
  routePolicy: {
    "GET /api/products/*": {
      replayable: true,
      classBoundPolicies: ["@method", "@path"], // require at least these + @authority
    },
    "POST /api/orders": { replayable: false },
    "GET /api/public/*": false, // skip verification entirely
    default: { replayable: false }, // require auth on all other routes
  },
});
```

Matching order:

1. Exact match on `"METHOD /path"`.
2. Wildcard match (`*`).
3. `default` policy (if set).
4. No match + no default → opportunistic (passthrough on failure).

A value of `false` skips verification. A `VerifyPolicy` object requires verification — returning `401` on failure.

<Callout>
  Both `/erc8128/verify` and `/erc8128/invalidate` enforce non-replayable, request-bound signatures — this is not configurable.
</Callout>

## Replayable Signatures

By default, every signature includes a nonce and can only be used once. For short-lived automation or backend-to-backend calls where re-signing each request is impractical, routes can opt into replayable signatures via `routePolicy`.

When any route allows replayable signatures, the plugin automatically enables:

- The `/erc8128/invalidate` endpoint for revoking signatures.
- Server-side verification caching so repeated use of the same signature skips expensive re-verification.

```ts title="auth.ts"
erc8128({
  verifyMessage: publicClient.verifyMessage,
  routePolicy: {
    "GET /api/products/*": {
      replayable: true,
      classBoundPolicies: ["@method", "@path"],
    },
    "POST /api/orders": { replayable: false },
    "GET /api/public/*": false,
    default: { replayable: false },
  },
});
```

<Callout>
  The `/erc8128/verify` and `/erc8128/invalidate` endpoints always require request-bound, non-replayable signatures regardless of route policy.
</Callout>

### Invalidation

Previously issued replayable signatures can be revoked via a signed `POST` to `/erc8128/invalidate`. Two modes are supported (one per request):

- **Per-signature** — revoke a single signature by its hex value.
- **`notBefore` timestamp** — reject all signatures created before a given time for the caller's key.

## Auto-Signing

When a `signer` is passed to `erc8128Client()` (as shown in the [installation step](#add-the-client-plugin)), every request through the Better Auth client is signed automatically — no manual header construction needed.

The signer can also be a function for lazy or dynamic wallet connections — return `null` to skip signing:

```ts
erc8128Client({
  signer: () => isConnected ? walletSigner : null,
})
```

On initialization, the client fetches `GET /.well-known/erc8128` to learn the server's replay and route policy configuration. By default, all requests use **non-replayable, request-bound** signatures regardless of server config. To opt into replayable class-bound signing when the server allows it, set `preferReplayable` and `components` — see [Signing Posture](#signing-posture).

### Signing Posture

The client controls its own signing posture via `preferReplayable` and `components`. These map to `@slicekit/erc8128`'s `SignerClientOptions` — the plugin forwards all non-managed fields (`ttlSeconds`, `label`, `contentDigest`, etc.) to `signRequest` automatically.

| `preferReplayable` | `components` | Behavior |
| --- | --- | --- |
| `false` (default) | *ignored* | Always request-bound, with nonce. |
| `true` | `undefined` (default) | Replayable + request-bound when server allows. Not cached. |
| `true` | `[]` | Replayable + class-bound with `@authority` only. Cached. |
| `true` | `["@method", "@path"]` | Replayable + class-bound with at least these + `@authority`. Cached. |

When `components` is set, the client merges it with the route's `classBoundPolicies` from the server config — the signed components are always the union of both sets.

```ts title="Backend agent — class-bound with minimum components"
erc8128Client({
  signer: agentSigner,
  preferReplayable: true,
  components: ["@method"],
  storage: sigCache,
})
```

### Signature Caching

When `preferReplayable` is `true` and `components` is set (even to `[]`), the client caches class-bound signatures and reuses them across requests — avoiding a cryptographic signing operation on every call.

Caching is controlled by the `storage` option:

| Value | Behavior |
| --- | --- |
| `"localStorage"` | Browser `localStorage` adapter (default when `localStorage` is available). |
| `Erc8128SignatureStore` object | Custom async-capable store — use for Node.js backends (Redis, database, in-memory Map). |
| `false` | Disable caching entirely. |

When omitted, `localStorage` is used if available, otherwise caching is disabled.

```ts title="Node.js backend with custom store"
const sigCache = new Map();

erc8128Client({
  signer: myAgentSigner,
  storage: {
    get: (keyId) => sigCache.get(keyId) ?? null,
    set: (keyId, entries) => sigCache.set(keyId, entries),
    delete: (keyId) => sigCache.delete(keyId),
  },
})
```

Each keyId maps to an **array** of cached signatures — different routes may require different class-bound components, so multiple valid entries can coexist until they expire. The `Erc8128SignatureStore` interface methods can return promises for async backends:

```ts
interface Erc8128SignatureStore {
  get(keyId: string): CachedSignature[] | null | Promise<CachedSignature[] | null>;
  set(keyId: string, entries: CachedSignature[]): void | Promise<void>;
  delete(keyId: string): void | Promise<void>;
}
```

A cached signature is reused only when:

1. It has not expired (with a configurable safety margin — `expiryMarginSec`, default 10s).
2. Its signed components satisfy the target route's `classBoundPolicies` from the server config.

When no cached entry covers the components required by a route, the client signs fresh and **appends** the new signature to the store alongside the existing entries. Expired entries are pruned automatically on each cache access. The `clearSignatureCache()` action removes all entries for the current signer.

## Error Handling

When verification is required and fails, the response includes:

```json
{
  "error": "erc8128_verification_failed",
  "reason": "expired",
  "detail": "Signature has expired"
}
```

Along with `Accept-Signature` and `WWW-Authenticate` headers indicating the expected signature components.

## Storage

The plugin manages three types of ephemeral data — all with bounded lifetimes tied to signature validity:

| Concern | Purpose | Durability |
| --- | --- | --- |
| **Nonce tracking** | Prevent replay of non-replayable signatures | Security-critical |
| **Signature invalidation** | Revoke replayable signatures | Security-critical |
| **Verification cache** | Skip re-verification for known-good replayable signatures | Performance only |

### Secondary Storage

When Better Auth's [`secondaryStorage`](/docs/concepts/session-management#sessions-in-secondary-storage) is configured (e.g. Redis), **all three are stored there by default** — with TTL-based auto-cleanup. This is faster than database queries and eliminates the need for manual cleanup of expired records.

To also persist nonces and invalidation records to the database (dual-write with secondaryStorage as fast read-through), set `storeInDatabase`:

```ts title="auth.ts"
erc8128({
  verifyMessage: publicClient.verifyMessage,
  storeInDatabase: true, // [!code highlight]
})
```

This follows the same pattern as Better Auth's [`session.storeSessionInDatabase`](/docs/concepts/session-management#sessions-in-secondary-storage).

| `secondaryStorage` | `storeInDatabase` | Nonce | Invalidation | Cache |
| --- | --- | --- | --- | --- |
| Not configured | — | Database | Database | Database + in-memory |
| Configured | `false` (default) | secondaryStorage | secondaryStorage | secondaryStorage |
| Configured | `true` | Database + secondaryStorage | Database + secondaryStorage | secondaryStorage |

<Callout>
For production deployments with multiple server instances, configure `secondaryStorage` (e.g. Redis) so nonce tracking, invalidation, and verification caching are shared across all instances.
</Callout>

## Options

### Server

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `verifyMessage` | `VerifyMessageFn` | *required* | Signature verification function (use viem's `publicClient.verifyMessage` — handles both EOA and ERC-1271 smart contract signatures). |
| `defaultPolicy` | `VerifyPolicy` | — | Default verification policy for middleware. |
| `routePolicy` | `Record<string, VerifyPolicy \| false>` | — | Per-route middleware policy map — see [Route Policy](#route-policy). |
| `sessionExpiresIn` | `number` | — | Session TTL in seconds (for `/erc8128/verify`). |
| `maxValiditySec` | `number` | `300` | Maximum signature validity window (seconds). |
| `clockSkewSec` | `number` | `30` | Allowed clock skew (seconds). |
| `storeInDatabase` | `boolean` | `false` | When `secondaryStorage` is configured, also persist nonces and invalidation to the database. See [Storage](#storage). |
| `cacheSize` | `number` | `10000` | Max entries in the in-memory verification cache. Ignored when `secondaryStorage` is active. |
| `emailDomainName` | `string` | From `baseURL` | Domain for auto-generated user emails. |
| `anonymous` | `boolean` | `true` | If `false`, email is required on verify. |
| `ensLookup` | `Function` | — | ENS resolver for new user name/avatar. |

### Client

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `signer` | `EthHttpSigner \| () => EthHttpSigner \| null` | — | Wallet signer for auto-signing. Without this, the plugin is type-only. |
| `preferReplayable` | `boolean` | `false` | Whether to prefer replayable signatures when the server allows it — see [Signing Posture](#signing-posture). |
| `components` | `string[]` | — | Minimum class-bound components. `undefined` = request-bound only; `[]` = class-bound with `@authority`; `["@method"]` = at least `@authority` + `@method`. |
| `storage` | `"localStorage" \| Erc8128SignatureStore \| false` | auto | Where to cache replayable signatures — see [Signature Caching](#signature-caching). |
| `storagePrefix` | `string` | `"erc8128"` | Key prefix for the built-in `localStorage` adapter. |
| `expiryMarginSec` | `number` | `10` | Seconds before expiry to consider a cached signature stale. |
| `ttlSeconds` | `number` | — | Signature TTL in seconds. Forwarded to `signRequest`. |
| `label` | `string` | — | Signature label. Forwarded to `signRequest`. |
| `contentDigest` | `"auto" \| "recompute" \| "require" \| "off"` | — | Content-Digest handling mode. Forwarded to `signRequest`. |

## Endpoints

| Method | Path | Description |
| --- | --- | --- |
| `POST` | `/erc8128/verify` | Verify a signed request, create/link user, start session. |
| `POST` | `/erc8128/invalidate` | Invalidate replayable signatures. Available when any route policy allows replayable. |
| `GET` | `/.well-known/erc8128` | Discovery metadata (algorithms, policies, endpoints). |

## Schema

### `walletAddress`

| Field | Type | Description |
| --- | --- | --- |
| `userId` | `string` | Reference to `user.id`. |
| `address` | `string` | Ethereum address. |
| `chainId` | `number` | EVM chain ID. |
| `isPrimary` | `boolean` | Primary wallet flag. |
| `createdAt` | `date` | Creation timestamp. |

### `erc8128Invalidation`

Stores both per-keyId invalidation timestamps and per-signature invalidation records.

| Field | Type | Description |
| --- | --- | --- |
| `keyId` | `string` | ERC-8128 key ID (`erc8128:<chainId>:<address>`). |
| `signature` | `string` | Signature hex for per-signature invalidation. Empty for per-keyId `notBefore` rows. |
| `notBefore` | `number` | Unix timestamp — signatures created before this are rejected. `0` for per-signature rows. |
| `expiresAt` | `number` | Unix timestamp when this invalidation record can be cleaned up. `0` for per-keyId rows. |
| `updatedAt` | `date` | Last update timestamp. |
